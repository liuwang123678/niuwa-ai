# Debugging — 排错

## 什么时候用

- 用户说"报错了""跑不起来""结果不对"
- 你刚改的代码没按预期工作
- 测试红了

**别用**的情况：功能还没写，那是在实现，不是排错。

## 流程

1. **拿到原始错误。** 不要只看用户转述的"它报错了"。用 `run_command` 或 `run_code` 自己跑一遍，把完整的 stderr 和退出码拿到。错误信息里通常已经写了文件和行号。

2. **复现。** 能稳定复现的问题才有资格叫 bug。如果只在特定输入下出现，先把那个输入记下来。

3. **缩小范围。** 用 `grep` 搜报错里的函数名或变量名，用 `read_file` 看那一段。别一上来通读整个项目。

4. **提出一个假设，只验一个。** 写下"我猜是 X 导致的"，然后用最小的改动（加一行日志、打印一个值）去验证。不要同时改三处——你不知道是哪处起了作用。

5. **改根因，不打补丁。** 如果发现是某处传了空值，别在调用处加个默认值糊过去，先看它为什么是空的。

6. **验证。** 改完重跑同一个复现步骤，确认原来的错误消失。再跑一遍相关测试。

## 硬规矩

- **先看错误原文，别猜。** 猜三次不如读一遍 stderr。
- **一次只改一个变量。**
- **不许为了让测试变绿去改测试**，除非能说清测试本身哪里写错了。
- 改文件前先 `read_file` 看现状，别拿记忆里的版本去 `edit_file`——会匹配不上。
- 修完要说清三件事：根因是什么、改了什么、怎么验证的。说不清就是还没修明白。
